# 高 FPS 下的移动跳动与保存停顿

## 本轮症状

用户确认所有测试版本都有不流畅现象；当前使用回拉修正版，垂直同步下 FPS 仍在 115 以上，但移动看起来断续。另有右下角“世界保存中”时无人机停止响应，保存结束后恢复的问题。

这两类现象分别涉及显示姿态的连续性和服务端保存期间的更新延迟。本轮交付 `0.1.1-playtest.3`，直接修正已确认的客户端姿态更新缺陷；保留原版存档流程，通过隔离测速区分保存停顿。

## 移动画面的修正

Minecraft 1.21.11 的基础 `Entity.getInterpolation()` 返回 null。旧无人机未覆盖该方法，因此收到位置更新时 `moveOrInterpolateTo` 直接调用 `setPos`；原 `getPosition(partialTick)` 只能在旧位置和当前位置间计算，不能阻止两帧之间收到的包改变当前渲染目标。

旧姿态逻辑还同时在客户端 tick 和渲染 getter 中重设上一帧/当前帧。一个新遥测包在两次渲染之间到达时，会改变尚在绘制中的区间，下一次 tick 又推进一次。即使每秒渲染 120 帧，画面也会跟着这些跳变抖动。

新版：

- 客户端使用原版 `InterpolationHandler(this, 1)` 排队位置更新，直到下一次客户端 tick 再应用目标；服务端飞行物理与控制指令不变。
- 整批遥测数据赋值完成后，将俯仰、偏航和横滚一起加入待处理姿态。tick 同时推进显示区间；渲染只读取区间，不修改历史。
- 角度沿 ±π 的短弧插值；停止接收更新后到达并保持已有端点，不预测未发生的飞行。
- 客户端直接定位、瞬移或网络大距离校正会清除旧的待处理目标，避免下一帧回到旧路线。

该设置使用一个 50 毫秒显示插值区间。一个包到达后，等待下一次 tick 加上当前显示区间，可能在约 50–100 毫秒后到达对应端点；持续 20 Hz 更新时约有一个姿态 tick 的显示缓冲。已有相机延迟设置仍有效，因此实际手柄感受需要本轮游玩确认。此次修正不等同于增加 FPS，也不消除服务端长时间停顿。

## 保存机制的排查与边界

本机原 FPV 日志使用的 Mod 已为 `0.1.1-playtest.2`；它记录了 `Saving and pausing game...`，并在一次保存之后记录服务端落后约 2128 毫秒。不能仅凭右下角保存图标判断是定时自动保存；进入暂停、窗口失焦、自动保存和退出都会涉及保存。

本地映射后的 Minecraft 1.21.11 代码表明：

- 普通自动保存调用 `saveEverything(true, false, false)`，不强制等待全部区块 IO 完成。
- 区块快照、玩家 NBT、实体 NBT 和世界元数据仍有服务端同步工作。区块序列化/区域文件写入已有后台工作线程。
- 进入单人暂停调用 `saveEverything(false, false, false)`。退出/显式完整保存的 flush 路径会等待待写区块和实体落盘。
- 无人机保存的是有界的配置、电池、转子及气动标量，不把黑匣子 CSV 历史塞入存档。本 Mod 没有替换原版世界保存。

因此，不应把保存时的世界读写整体挪到任意后台线程，也不应取消自动保存或退出时的完整写入。若服务端被保存阻塞，无人机的权威状态也会暂停更新；客户端帧率可以保持很高。纯镜头平滑不能让这段时间的实际飞行继续。

保存优化的后续判断应依据同步区块快照、实体序列化、玩家/世界元数据写入、GC 与渲染耗时的分段数据。若快照集中处理确实占主导，可以评估服务端按 tick 分批处理自动保存；必须保留脏区块检查、卸载保存、手动保存和退出时的完整排空，并验证立即退出重进的数据一致性。本轮没有以未经验证的保存改写交付给用户。

本轮实际 JFR 结果将优先级指向同步文件 IO：普通保存范围内的 33 个服务端采样中，32 个落在原生文件系统调用，1 个在玩家 NBT 保存执行路径；按完整调用栈归类为统计 JSON 16 个、世界元数据 NBT 9 个、玩家 NBT 7 个原生采样。采样次数不是耗时百分比。保存范围内、同一服务端线程的 FileWrite 事件直接记录约 **1510.49 ms**，其中世界元数据约 **1263.49 ms**、玩家 NBT 约 **247.00 ms**；打开、关闭、替换文件的阻塞另有采样证据。没有观察到区块快照成为该普通保存的主要热点，因而这版不以改写区块批量保存作为解法。

后续应先对照本机文件系统写入延迟与普通游玩中的保存记录；这份合成世界采样不足以断言某个磁盘、杀毒软件或硬件故障。若要实现异步统计/玩家/世界元数据写入，需要在服务端生成稳定快照，串行保证写入顺序和文件替换，处理失败，并在手动完整保存、退出和关闭时等待队列排空。当前证据已定位研发方向，但这类持久化改动仍需单独验证后交付。

原版 F3+P 可切换窗口失焦时的自动暂停；它与关闭自动保存不同。只有日志及复现确认卡住由切出窗口触发时，才用该设置判断，手动暂停与正常自动保存仍保留。测试实例沿用原视频和手柄设置，以便对照，不预先降低渲染/模拟距离。

## 验证

602 项 Fabric 单元测试与 9 项服务端 GameTest 通过。纯姿态历史回归覆盖两帧间到包、同 tick 多包取最后完整目标、±π、丢失更新以及重置。真实客户端流程构造无人机，直接调用客户端的元数据、相对移动、位置同步和瞬移消息处理方法，检查完整姿态批次、区间起点/中点/终点与瞬移清除待处理目标；普通起飞、FPV、模式切换及上锁流程也通过。客户端测试使用 Fabric 的合成操作，未测物理手柄、真实网络到包抖动或显示器流畅度，不能当作帧率基准。

生产 JAR 在 Minecraft 1.21.11、Fabric API 0.141.6+1.21.11、LWJGL 3.3.6 下完成普通启动、资源与声音加载、主菜单截图和正常退出，进程退出码为 0；安装实例的 68 项运行时文件与生产 JAR 均通过哈希核对。

保存测速使用单独正常客户端和合成世界；不运行 Fabric 客户端 GameTest 的受控 tick 循环，不读取用户存档，不改变原版保存。固定超平坦场景包含一架地面上锁无人机，在保存前重新修改 25 个区块；生成世界本身也可能产生其他脏区块，不能将保存总量认作只有 25 个。

未开启 JFR 的参考运行中，普通保存同步调用耗时 **1645.15 ms**，期间服务端无人机更新间隔达到 **1659.16 ms**，客户端提交到服务端的测试任务最多等待 **1603.09 ms**。同时，1746 个覆盖保存期间的渲染帧间隔最大为 **3.75 ms**。这说明服务端保存可令实际飞行停止更新，而画面渲染继续；它是合成场景下的机制复现，并非用户原世界的完整诊断。

显式 flush 耗时 **445.77 ms**，完整退出阶段约 **13.96 s**，两者与普通保存分别记录。两次正常客户端运行都通过方块修改、无人机 UUID、所属玩家、模型、质量和名称的退出重进检查；该检查验证完整写入后的持久化，不验证突然断电时普通异步保存的数据完整性。第二次开启 JFR 的运行普通保存耗时 **3421.71 ms**，包含采样开销及运行差异，不应与首轮相除后解释成稳定的性能比例。

隐藏窗口采用原版最高帧率选项 260；这个最大选项实际关闭原版 FPS 限制，数字不是 260 Hz 上限。隐藏窗口帧间隔不代表用户垂直同步下的实际显示效果。两份正常客户端报告随验证记录交付。
